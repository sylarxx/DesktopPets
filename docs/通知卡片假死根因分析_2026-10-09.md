# 通知卡片假死与无法关闭：根因分析及候选修复

## 结论与证据边界

现场已确认安装版本为 **1.0.54**，内网电脑会定时锁屏。用户报告：有提醒时机器人招手，但没有可见卡片；退出重进后出现“未能标记已读，请检查网络后重试”，反复点击不能收起。

发现两个可以由代码和受控复现确认的缺陷：显示状态提前被认定成功，以及已读接口的非幂等返回被客户端误判。它们解释了这组症状为何能发生，不能仅凭截图证明现场那一次一定同时命中了两者。现场 HTTP 响应、WebView2 状态和窗口日志尚未取得。

修复已写入当前工作区并通过本地检查，正在制作 **1.0.55 管理员/SYSTEM 静默推送 MSI**，升级基线为已交付的 1.0.54。现有 1.0.54 安装包不包含本次修改。后端检出副本仅用于核对契约，没有修改或部署后端。

## 1. 为什么招手不等于卡片真的出现

1.0.54 的流程是：隐藏卡片接收内容 → Vue 刷新并读到非零布局 → 发回布局确认 → 原生显示命令返回成功 → 协调器写入“可见” → 机器人招手。

隐藏时读到布局，只证明 DOM 能排版；原生显示命令成功，没有确认卡片渲染器在显示之后恢复了帧。锁屏后可能出现机器人窗口正常、独立卡片窗口尚未恢复的状态，旧流程仍会提前招手。另外，原生恢复隐藏卡片时没有立即撤销协调器的可见状态，期间仍可能招手。

相关代码：`src/utils/notification-delivery.ts`、`src/views/MascotNotificationWindow.vue`、`src/App.vue`、`src/views/MascotWindow.vue`、`src-tauri/src/main.rs` 和 `runtime_recovery.rs`。

修复保留隐藏布局确认，再增加**原生 show 之后的两次动画帧与原生可见性确认**。原生确认命令校验调用窗口、当前显示批次、窗口状态和实际 HWND 可见性。协调器只接受当前批次的确认；隐藏或重建立即撤销可见状态，迟到的确认无法恢复已经撤销的招手。

没有帧确认时仍最多尝试三次、整轮最多十秒，随后收起不可用窗口、保留未读消息并释放队首。已显示过但后来被原生隐藏的卡片，可以再进行一轮有界显示；重复 ready/hide 事件不会重置正在进行的尝试。菜单和托盘隐藏意图先处理，再判断是否需要恢复。

动画帧与 HWND 可见性仍不能证明真实机器上的 GPU 合成像素，因此不能代替 Windows 实机观察。

## 2. 为什么“知道了”会一直失败

后台接口返回的是“这次是否更新了未读行”，而不是“最终是否已读”：

```java
return sysMessageMapper.markReadByIds(ids, SecurityUtils.getUsername()) > 0;
```

SQL 包含以下条件：

```sql
WHERE receiver_emp_no = #{receiverEmpNo}
  AND deleted_flag = 0
  AND msg_status = 0
  AND id IN (...)
```

当浏览器已读同一消息，或上一次请求超时但后台实际写成功，再点就会更新零行，返回 `code:200, data:false`。1.0.54 只接受 `data:true`，把已经满足的状态当成失败，保留卡片。之后每次重试仍更新零行，仍失败。

App 还把已读未确认、401、403、超时及网络失败都显示成“请检查网络后重试”。因此截图里的这句话不能证明内网断了。

后台证据来自本地检出副本 `hl-agent-plat`：

- `gpt/src/main/java/com/ruoyi/gpt/controller/SysMessageController.java:32`：PUT `/sys-message/read` 返回 `R<Boolean>`。
- `gpt/src/main/java/com/ruoyi/gpt/service/impl/SysMessageServiceImpl.java:80`：根据更新行数返回成功。
- `gpt/src/main/resources/mapper/gpt/SysMessageMapper.xml:59`：只更新当前账号未读、未删除的消息。
- service 文件最近一次本地历史变更为 `e1cb8c8`，日期 2026-07-03。尚未核对现场部署是否与这个检出副本一致。

客户端修复仅在明确收到 `false` 时，查询当前登录账号的已读列表；只有看到同一 ID 且 `msgStatus=1` 才确认成功。最多五页、一百行，共用十秒期限。查不到、返回其他结构或请求失败都不会假装已读。401、403、超时分别给出对应提示。

长期应把后台接口改为幂等：更新后确认所选所有消息属于当前账号、没有删除且最终已读，再返回成功。不能把“更新零行”无条件改成成功，否则会掩盖不存在或不属于当前账号的 ID。

## 3. 为什么退出重进仍会出现

1.0.54 保存当前消息及队列，渲染器恢复和正常重启都会读取同一快照。未读轮询不会纠正“快照还在，但后台已经读过”的旧队首；内存去重记录重启后也重新建立。

重启能使窗口重新出现，却不能自动解决已读契约冲突。提醒仍受原有三十分钟有效期限制，不能把“一直点不掉”解释为代码里存在永不过期的消息。

新增独立关闭按钮：即使正在请求或同步失败，也能收起卡片。关闭不更改后台已读状态；本地只保存账号、消息 ID、创建时间及截止时间，不保存正文或凭证。记录按账号隔离、最多 256 条，不延长消息有效期。

初始恢复、解锁恢复及新消息进入队列前均检查关闭记录，避免关闭的同一消息马上再弹出。旧请求的结果不能把关闭的卡片放回来，也不能覆盖下一张卡片的提示。

## 4. 上次修复覆盖与这次遗漏

复查当前仓库及先前交付记录，1.0.54 已处理锁屏/解锁、渲染器无响应、进程退出、窗口重建和队列保存。它没有完成本次新增的显示后确认和已读状态核对。

原生健康观察器虽独立运行，窗口修复仍需要主 UI 线程。若主 UI 消息循环本身卡住，就执行不了修复。新增单探针超过 25 秒未执行的一次性记录，锁屏/休眠不计入，恢复后重启宽限；它帮助区分宿主 UI 停滞与卡片渲染器停滞，不增加 UI 排队任务。没有把主线程死锁认定为现场已证实原因，也没有声称这一分支已经修复。

正式版原有 `desktop-diagnostic.jsonl` 禁用行为保持。按本次用户确认，少量运行记录采用固定两文件，每个最多 64 KiB、总量最多 128 KiB，写入前检查并覆盖轮换，旧超限文件先清理。不记录正文、用户 ID、访问地址、异常原文或登录凭证；只记明确枚举的投递失败阶段、已读核对结果和原生恢复事件。安装后启动脚本原有无限追加日志已经移除并增加旧文件定点清理。

## 6. 仍需现场完成的验收

后续 Windows 候选包应由管理员/SYSTEM 部署。在这台定时锁屏电脑上验证：锁屏期间产生新提醒，解锁后卡片与招手一致；单击、双击、拖动及输入草稿正常；没有透明窗口挡住其他应用。

再验证：浏览器先标为已读后桌面点击“知道了”；请求期间断网或超时后关闭并重启。应可收起，后台未确认时不假装已读，关闭的同一消息不再立刻重弹。

若仍出现首发无卡片，应在退出前保留 `%LOCALAPPDATA%\com.huali.ai.mascot\logs\runtime-health.jsonl` 和 `.1`，由管理员确认 Windows/WebView2 版本及故障时间。当前无法直接读取这台 Windows 电脑的日志，真实定时锁屏验收尚未完成。
