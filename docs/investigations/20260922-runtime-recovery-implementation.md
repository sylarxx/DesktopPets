# 1.0.54 锁屏和界面故障恢复实施

对应调查：`20260922-lock-screen-stall.md`。调查基线为 1.0.53；本文记录后续修复，最终 Windows 执行结果以对应提交的 CI 和随包证据为准。

## 故障链与改动

| 缺口 | 本次处理 | 保护条件 |
| --- | --- | --- |
| 展示失败的消息继续占住队首，单击按“存在消息”返回 | 失败消息移入待恢复集合，后续消息可继续；单击按正在显示的消息卡片判断 | 保存后台未读状态及原到期时间 |
| 锁屏调度暂停后耗尽原 10 秒预算，迟到 ACK 无法重启 | 原生会话状态控制 suspend/recover，每个恢复 epoch 只开放一次新的有限投递 | 普通重复消息、ready、旧 ACK 不重置预算 |
| JavaScript 失活后自己的定时器无法救自己 | 单独的 Windows 消息线程接收 WTS/电源事件，每 5 秒向 UI 主线程投递至多一个检查 | 不持有状态锁等待同步窗口调用，不堆积检查任务 |
| 隐藏/可见与界面响应混在一起 | 即时 JS 回执与两帧后的回执分开；可见窗口检查帧回执，隐藏窗口不因不绘制被重建 | 锁屏停判，启动和恢复留 35 秒宽限；连续无响应阈值为 25 秒 |
| 原生窗口还在而渲染进程退出 | 接入 WebView2 ProcessFailed：无响应/渲染退出先重载，浏览器退出直接重建 | 每窗口每轮最多两次；正常响应持续 120 秒后清零，隐藏窗口也可通过 JS 回执恢复预算 |
| 重建窗口导致消息、任务丢失及旧回调干扰 | 各窗口独立、按账号保存必要状态；native generation、renderer instance、runtime epoch 和通知 generation 分别防旧结果 | 不保存凭据到恢复快照，不重发写请求；系统时钟回拨时从原生通知序号继续 |
| 解锁后仍信任旧 WebSocket 的 OPEN | 强制替换两路连接并做最多 5 页/100 条/10 秒补取 | 保留去重，旧 socket 回调与旧轮询结果失效 |
| 原生显示绕开框架，隐藏和样式更新仍走框架，双方可见状态不一致 | 统一走 Tauri 显示/隐藏；四个窗口配置 focus:false，主动操作另外 set_focus | Windows 原生门禁同时检查卡片确实可见、原隐藏输入框不露出和恢复不抢焦点 |

窗口可见状态不一致不是纯推测：第一次故障注入的截图和原生回执显示，恢复浏览器/渲染进程后，初始隐藏的输入框意外露出。检查锁定依赖 Tao 0.35.3 的 Windows 实现，`set_visible` 按缓存的 VISIBLE 位计算差异，没有差异时不调用隐藏；旧的 `SWP_SHOWWINDOW` 绕过了该缓存。该发现促使暂停初次 1.0.54 打包，统一窗口 API，并加严后续 MSI 门禁。首次试验通过进程恢复检查，不作为最终窗口状态正确的交付证据。

重载/重建期间隐藏透明窗口前先启用点击穿透，必要时在屏幕外完成初始化。应用挂载完成后恢复窗口原位置与尺寸，按原意图显示机器人/面板；通知和菜单仍通过自己的布局握手显示。重建最后一个 WebView 不退出托盘宿主，用户主动“退出”仍立即退出。

创建控制器临时失败时，旧窗口已经不存在；原生监测仍检查该窗口的恢复记录，在同一宽限期和最多两次预算内再创建一次，不因“找不到 HWND”永久跳过。Windows 故障脚本包含一次明确的创建失败，要求第二次成功、主程序不变且预算恰好为两次。

输入草稿沿用既有存储；通知与任务快照在变更时同步保存。恢复中的任务操作如原先仍在处理，提示先确认工作台结果，不自动再次提交。注销清除恢复快照，账号不匹配的快照不读取。

## 现场边界

未取得 1.0.53 原问题机的当晚转储，不能把 WebView2 崩溃、GPU 故障或宿主主线程死锁当作已经证实的起因。此次修复针对已复现的状态链及缺失的原生恢复机制。

健康日志位于当前用户应用日志目录的 `runtime-health.jsonl`，达到 256 KiB 后轮转，最多保留当前文件和一个备份。旧的带敏感字段的诊断 writer 保持关闭。日志中 `session-inactive/session-interactive`、`renderer-process-failed/browser-process-failed`、`renderer-reload/window-recreate`、`renderer-mounted-after-repair` 可区分后续故障分支。

原问题机验收应保留真实锁屏过夜，并在解锁前后产生新的有效提醒；同时检查单击输入、双击工作台、拖动、托盘、任务和草稿。已有超过 30 分钟的消息不补弹属于现有产品规则。

故障注入前先通过实际鼠标操作把焦点移到应用外；恢复后用 Windows `GetForegroundWindow` 所属进程再次确认未激活助手。此项与截图、DOM 回执分别检查，不能仅凭某一个 WebView 报告自己没有焦点判定通过。

程序二进制和 MSI 均以该次通过的构建为准。之后的交付整理只补齐压缩包中的 `Test-HualiAIRuntimeRecovery.ps1` 并记录验收结果，不改动 MSI；本地交付目录保存重新核对后的 MSI 和 ZIP 校验值。
